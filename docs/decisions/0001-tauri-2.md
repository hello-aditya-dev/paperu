# ADR 0001: Choosing Tauri 2 for the desktop shell

- **Status:** Accepted
- **Date:** Foundation pass (pre-`0.1.0`)
- **Decision owner:** Integrator
- **Affected code:** `apps/desktop/src-tauri/`

## Context

Paperu is a Windows-first, local-first file workspace. The defining
constraints of the desktop shell decision were:

1. **Windows is the primary release target.** The first installer
   shipped must be a native Windows executable that users double-click
   to install. macOS and Linux are not first-class targets for the
   foundation (see `KNOWN_LIMITATIONS.md`).
2. **The backend must be Rust.** The non-destructive file model, the
   atomic finalization primitive, the cancellation-aware task engine
   and the local-first security invariants (`LOCAL_FIRST = true`,
   `REMOTE_UPLOAD_PERMITTED = false`) need to live in native code, not
   in a JS runtime. Rust gives us memory safety, a strong type system,
   and a credible story for shipping a single binary with no embedded
   interpreter.
3. **The frontend is React + TypeScript.** Reusing the team's UI
   tooling (React 19, Vite, vitest, `@testing-library/react`) is more
   valuable than adopting a niche UI framework tied to a specific
   shell.
4. **The binary must be small and self-contained.** Users will not
   install a 200 MB runtime alongside a tool that inspects a file.
5. **The shell must not pull network plumbing into the bundle by
   default.** A local-first product cannot ship a desktop shell that
   assumes or bundles cloud dependencies the way Electron-style shells
   often do.
6. **Capabilities must be restrictive by default.** The frontend
   webview should not be able to open arbitrary sockets, spawn
   processes, or read arbitrary paths without going through a typed
   IPC boundary.

The alternatives considered:

- **Electron + Node sidecar.** Mature, well-known, but ships a
  Chromium snapshot and a Node runtime per app. The minimum
  installer is large (tens of MB) and Node gives the frontend more
  ambient power than the threat model allows. The Rust backend would
  have to run as a sidecar process, complicating lifecycle and IPC.
- **Qt / GTK native.** Gives the smallest binary and the strongest
  native feel, but forces a non-web UI stack and abandons the
  React/TypeScript investment. Slower to iterate on UI.
- **Flutter Desktop.** Strong single-language story, but the Rust
  backend would be a foreign-process binding (FFI over Dart), the
  Windows installer story is still maturing, and the team's UI
  tooling does not transfer.
- **A pure Rust native shell (eg. `slint` or `iced`).** The smallest
  possible footprint, but no mature React/Vite tooling, slower UI
  iteration, and a smaller pool of UI components. Acceptable for a
  narrow tool, not for a workspace product.

## Decision

Paperu's desktop shell is **Tauri 2**, with a Rust backend and a
React 19 + TypeScript frontend rendered in the platform webview.

The shell is gated by the `tauri-runtime` cargo feature
(see `apps/desktop/src-tauri/Cargo.toml`). Without the feature, the
core modules (`errors`, `contracts`, `filesystem`, `database`,
`settings`, `tasks`, `logging`, `security`, `licensing`) compile and
test on any platform. With the feature, the Tauri command handlers and
the desktop entry point (`paperu::run()`) are compiled and linked
against the platform webview and windowing libraries.

The frontend is the only thing rendered in the webview. It calls into
Rust exclusively through the typed IPC client at
`apps/desktop/src/lib/ipc.ts`, which imports from `@paperu/contracts`.

Capabilities (`apps/desktop/src-tauri/capabilities/default.json`)
grant only `core:default` and `dialog:allow-open` to the main window.
The CSP (`tauri.conf.json`) restricts `connect-src` to `'self'
ipc: http://ipc.localhost` — IPC is the only non-self connection
allowed.

## Consequences

### Positive

- **Small binary.** Tauri ships the platform webview (WebView2 on
  Windows) rather than embedding a browser engine. The install
  footprint is dominated by the Rust code and the bundled SQLite
  amalgamation, not by a Chromium snapshot.
- **Webview-based UI reuses existing tooling.** React 19, Vite,
  vitest, `@testing-library/react`, ESLint, TypeScript all transfer
  directly. The frontend team is productive immediately.
- **Rust backend with no sidecar.** Commands are `#[tauri::command]`
  functions in the same binary. There is no IPC over a sidecar
  process; the boundary is the Tauri `invoke` channel, which carries
  serde-serialized JSON typed by `@paperu/contracts`.
- **Restrictive capabilities by default.** The capability file lists
  exactly what the frontend may call. The frontend cannot open a
  socket, spawn a process, or read an arbitrary path. A future
  capability must be added by the Integrator (capability files are
  Integrator-controlled; see `CONTRIBUTING.md`).
- **Strong separation of concerns.** The `tauri-runtime` feature flag
  means the entire core logic surface compiles and tests on Linux CI
  without webview or windowing dependencies. The Windows CI job runs
  the same gate with `--features tauri-runtime` and produces the
  installer.
- **Single, signed installer.** Tauri's bundler produces an MSI / NSIS
  installer on Windows. The build pipeline is documented in
  `docs/releases/workflow.md`.

### Negative

- **Platform system dependencies for development.** Building the
  `tauri-runtime` feature on Windows requires the WebView2 runtime
  (present on Windows 10/11 by default) and the MSVC toolchain
  (`x86_64-pc-windows-msvc`, pinned in `rust-toolchain.toml`).
  Building on Linux requires GTK and WebKitGTK dev packages; these
  are not needed for the core-only (`rust-core` CI) build, only for
  local Linux UI development.
- **Webview rendering differences.** The UI renders in the host
  webview, not a bundled Chromium. Edge WebView2 on Windows is the
  release target; older Windows versions without WebView2 must
  install it (a one-time system update). Visual differences between
  WebView2 and the Linux WebKitGTK used in dev are possible and must
  be checked on Windows before release.
- **Restrictive capabilities slow some features down.** Any new
  native capability the frontend needs (clipboard, notifications,
  shell open) must be added to the capability file and reviewed by
  the Integrator. This is intentional friction; it is also friction.
- **Tauri 2 is newer than Tauri 1.** The 2.x line is the supported
  line, but third-party plugins and ecosystem docs are still catching
  up. The foundation's surface (`tauri`, `tauri-plugin-dialog`,
  `tauri-build`) is stable; future plugins must be evaluated per
  ADR `0008-dependency-policy.md`.

### Neutral

- **No embedded updater today.** The Tauri updater plugin is
  disabled (`createUpdaterArtifacts: false`). A future ADR will
  decide whether the updater ships, and how its signature is
  verified. See `docs/releases/workflow.md` for the signing plan.

## Alternatives considered and rejected

- **Electron.** Rejected on binary size and on the Node-sidecar model
  that conflicts with the restrictive-capability threat model.
- **Qt/GTK native.** Rejected on UI tooling investment and iteration
  speed.
- **Flutter Desktop.** Rejected on the FFI-over-Dart boundary and on
  the smaller component ecosystem for a workspace product.
- **Pure Rust native UI (`slint`, `iced`).** Rejected on UI iteration
  speed and tooling transfer.
